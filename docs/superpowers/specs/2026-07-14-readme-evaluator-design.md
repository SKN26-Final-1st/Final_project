# HumouR 평가용 README 설계

## 목표

평가자가 짧은 시간 안에 HumouR를 하나의 완성된 AI 채용 보조 서비스로 이해하고, 구현 근거·자체 sLLM의 차별점·검증 결과·한계를 저장소에서 직접 확인할 수 있게 한다.

## 독자와 평가 관점

- 주 독자: 최종 프로젝트 평가자와 기술 검토자
- 1순위 판단 기준: JD 작성부터 외부 리포트 공유까지 연결된 서비스 완성도
- 2순위 판단 기준: 자체 파인튜닝 sLLM과 LangGraph 기반 분석 파이프라인의 기술적 차별성
- 신뢰 기준: 코드·노트북·테스트·운영 설정·산출물로 역추적할 수 있는 주장만 사용

## 정보 구조

참고 템플릿의 15개 항목을 기계적으로 유지하지 않는다. 평가자의 의사결정 순서에 맞춰 다음 흐름으로 재구성한다.

1. 로고, 한 문장 정의, 핵심 성과 요약
2. 문제 정의와 해결 전략
3. 실제 사용자 여정과 구현 기능
4. 전체 시스템 및 LangGraph 분석 구조
5. 자체 sLLM 학습·추론 구조와 데이터 파이프라인
6. 운영 안정성·보안·배포 설계
7. 오프라인 평가 결과와 실패 사례
8. 데이터 모델·API·프로젝트 구조
9. 실행·검증·산출물 재현 방법
10. 팀 기여, 한계, 향후 확장, 책임 있는 사용

## 표현 원칙

- 자체 모델은 기반 모델 자체 개발이 아니라 `EXAONE-3.5-2.4B-Instruct`를 LoRA 파인튜닝한 sLLM이라고 정확히 표기한다.
- 평가 수치는 노트북에 저장된 오프라인 결과임을 명시하고 표본 수와 평가 버전을 함께 적는다.
- 현재 구현과 후순위 기능을 분리하고, 라이브 운영·보안 인증처럼 검증하지 않은 내용을 주장하지 않는다.
- 서비스 안정성은 비동기 처리, 동기 폴백, 상태 전이, 원자적 크레딧 처리, 인증·권한, 런타임 스키마 검증, 요청 취소의 실제 구현으로 설명한다.
- 채용 결과의 자동 의사결정 도구가 아니라 사람의 검토를 돕는 보조 시스템임을 명확히 한다.

## 핵심 근거

- 서비스 코드: `backend/`, `frontend/`
- 자체 sLLM: `llm/train_star_masking/`, `runpod/`
- 평가 결과: `llm/eval/`
- 데이터 수집·벡터화: `database/`
- 운영 구성: `.github/workflows/`, `.deploy/`
- 테스트·검증: `frontend/src/**/*.test.*`, `frontend/tests/e2e/`, `frontend/scripts/`
- 산출물: `outputs/interface-definition/`, `docs/`

## 시각 구성

- 기존 라이트/다크 로고를 `<picture>`로 제공한다.
- 사용자 여정, 시스템 구성, 분석 그래프, 핵심 ERD에 Mermaid를 사용한다.
- 표는 기능 범위, 운영 방어, 모델 평가, 팀 기여처럼 비교가 필요한 정보에만 사용한다.

## 승인 반영

사용자는 서비스 개발 완성도에 더 큰 비중을 두되 자체 sLLM을 큰 장점으로 강조하고, 참고 템플릿의 항목과 순서는 필요에 따라 제거·추가·수정하도록 승인했다.
